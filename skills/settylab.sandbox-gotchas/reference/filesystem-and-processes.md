# Sandbox filesystem, processes and channels

Detail behind §7-§9 of `settylab.sandbox-gotchas`. NFS behaviour that is not sandbox-specific (attribute caching, many mount entries per device, `st_dev` per node, setgid modes, hard-linked trees) is in `fh.storage-fast` → `reference/nfs-pitfalls.md`.

## Mounts and writability

- **The parent of your project bind is always read-only.** `/fh/fast/<lab>` is mounted `ro` permanently; the writable tree is a separate bind at your project path. After an `EROFS`, read the PROJECT bind's own row, not the parent's: `awk -v p="$SANDBOX_PROJECT_DIR" '$2==p{print $4}' /proc/mounts`. Never write-probe to find out.
- **A read-only incident is sandbox-local.** Compute nodes do not see the sandbox's binds, so Slurm jobs that ran through an RO window need no re-verification or re-queue. Check only what ran inside the sandbox during the window.
- **`/` is a writable private tmpfs, and `rm` at `/` may be denied by guards.** A relative path resolved after `cd /` really writes there (a test that removed a path guard wrote a full tree at `/c11`). Probe writability with `test -w`, never `touch`, and point any test that removes a path guard at an unwritable target.
- **After a mount repair, a long-lived process's cwd is broken in one of two ways.** DETACHED: `getcwd` fails (git rc 128, `os.getcwd` ENOENT) but writes work. RO FALL-THROUGH: path, dev:ino and `getcwd` look fine, and every RELATIVE write fails EROFS forever. Detect by mount id (`mnt_id` in `/proc/self/fdinfo` of an fd opened via `/proc/<pid>/cwd` vs a fresh open of the path), not by path, inode or builtin `pwd -P` (use `/bin/pwd -P`). Heal with an unconditional `cd -- "$PWD"` per loop iteration, write by ABSOLUTE path, and read each write's rc before using its output (a failed relative write once made four planted controls pass on an empty input).
- **The session scratchpad is on `/tmp`, a different filesystem from `/fh/fast`.** `mv` into the project is copy + delete; a 0555 subdir makes the delete fail (rc 1) after a complete copy. Keep dirs writable until after the move, `chmod 0555` at the destination, and after any failed `mv` run `sha256sum -c` at the destination before deciding anything.
- **`/tmp` may be shared between sandboxes** (landlock backend, `PRIVATE_TMP=false`). Code that `mkdir -p`s a fixed directory under `/tmp` and writes into it follows whatever another party pre-created: a planted symlink truncates a victim file, a planted FIFO hangs the writer. Check the directory's owner and mode, or create with `O_EXCL|O_NOFOLLOW` (`noclobber` does not stop a FIFO), and test against a hostile pre-created dir. A pure removal avoids the class.
- `~/.claude/sandbox-config/settings.json` is a read-only mount (EROFS) even though its directory accepts new files. Give the user the exact edit to make outside the sandbox; do not leave copies there.

## Processes and the shell

- **`/proc/loadavg`, `/proc/stat` and `top`'s `%Cpu(s)` line are the whole node.** bwrap does not namespace them: load ~33 on 36 cores sat beside ONE runnable process of ours and 62% idle CPU. Count your own tasks instead (`ps -u "$USER" -o stat= | cut -c1 | sort | uniq -c`). Load IS the right signal for contention you suffer: record it beside any timing-sensitive result, and treat a timing failure under high load as unreproduced. High load with idle CPU means I/O contention, not CPU. A load figure is stale once written; do not relay it.
- **`ulimit -u` counts the uid's processes HOST-WIDE, but `ps` shows only the sandbox namespace.** A fixed cap can be exceeded at fork time while a runaway (yours or another session's) is live: the command dies `fork: Resource temporarily unavailable` having never run, and that reads as a test failure. Use a relative cap: `cap=$(( $(ps -u "$USER" -o nlwp= | awk '{s+=$1} END{print s}') + 500 ))`. Recursion (count plateaus) and starvation (fork fails) share an exit code; call both void.
- **Read the exit word of a dead process.** `Aborted` = SIGABRT (it killed itself: heap, fork failure, V8 fatal), `Killed` = SIGKILL (OOM killer or `kill -9`), `Terminated` = SIGTERM (something asked). Timestamps mark when writing stopped, not when a process ended. A fork bomb does not yield to enumerate-then-kill: `kill -STOP` the session's pids until the count is stable, then `kill -KILL`.
- **`environment: line N: : command not found`** does not imply an exported function: bash 4.4 labels functions defined inside a `bash -c` string "environment" too, with 0-based line numbers. The sandbox's own `bash -c` staging produced one (a `\`-continuation became `\ `, a command named " ", visible as TWO spaces before the colon). Enumerate every `bash -c` in the chain and reproduce the generated string under the same bash.

## The tmux server is the sandbox

`bwrap` is PID 1 and runs `tmux new-session …` with `--die-with-parent`. Anything that ends the tmux server ends the whole sandbox: every agent window, every background service, and the user's own session, with no in-sandbox recovery.

- `tmux kill-server`, `kill-session` on the last session, and `kill-window` on the last window of the last session all do it. Enumerate from the hazard ("what ends the server?"), not from a verb list.
- `TMUX_TMPDIR` alone does not isolate a test server: inside a pane `$TMUX` outranks it (`-L`/`-S` > `$TMUX` > `TMUX_TMPDIR`). Use `env -u TMUX tmux -L <private> …`, and verify that `env -u TMUX TMUX_TMPDIR=/tmp/x tmux display -p '#{socket_path}'` does not print the default socket.
- Keep a private `TMUX_TMPDIR` short (`/tmp/tt-$$`): `sun_path` holds 107 bytes and scratchpad paths already exceed that, which turns every real-tmux test into a false "File name too long" FAIL.
- One recorded sandbox death on a saturated host had no attributable kill command in any transcript; record such a cause as undetermined rather than guessing.

## Network, mail and git transport

- **Network filtering in batch jobs is a property to check, not an assumption.** On compute nodes the sandbox's network filter has been observed to fall back to unfiltered, and the job log then carries a line such as `network filter fell back from 'filtered' to 'open'`. Read the job log for it. Do not argue a job is safe because it "cannot reach the network"; claim "no network used" only with evidence (code read, or a trace showing no non-loopback connect/sendto), otherwise write "filter open; network use not measured". A grep for the banner needs a control in the real line's form. If you see the fallback, report it to the user rather than testing the sandbox.
- **Outbound mail is disabled** (`mail` → "outbound mail is disabled in this configuration", exit 77; SMTP blocked). Email is not an escalation channel from inside; log with `logger` and tell the user in-session.
- **`git@github.com:` fails "correct access rights" while auth is fine.** `No user exists for uid N` first means `ssh`'s `getpwuid()` failed: the sandbox's filtered `/etc/passwd` lost your entry (a shared file rewritten under running sandboxes). Discriminate with `getent passwd "$(id -u)"` (rc 2 = NSS, not auth; `id` may still resolve your group). `ssh-keyscan` does not call getpwuid, so a keyscan probe stays green while `ssh` is dead. Workaround: HTTPS transport with the helper from §3 (`git remote set-url origin https://github.com/<org>/<repo>.git`). The fix is outside the sandbox: regenerate the file IN PLACE (`cat new > file`); `sed -i` makes a new inode that running sandboxes do not see.
- **A `git clone` on NFS under a short `timeout` dies in checkout** (rc 124, empty index, clone dir left behind). Give clones a long bound, run them in the background, and check completion.
- Do not run agent_sandbox's own namespace/mount test suite on a shared login host: it creates and enters throwaway namespaces and mounts repeatedly, which can trip endpoint security. Open the PR and let CI run it (operator ruling, 2026-10-21).
